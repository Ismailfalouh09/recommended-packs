# Backend Global Review

Date: 2026-07-02

## Architecture Summary

This repository is a NestJS backend for a beauty ecommerce recommendation engine. The application is organized into feature modules under `src/modules`, with controllers delegating to services and data access routed through `PrismaService`. Validation is DTO-based with `class-validator` and `class-transformer`, and Swagger/OpenAPI is generated by `scripts/generate-openapi.ts` through `src/common/swagger/openapi.config.ts`.

The Prisma schema defines the main ecommerce domain: attributes and quiz questions, anonymous customer profiles, products, product references, packs, pack configurations, recommendations, COD orders, admin users, media assets, wishlist items, reviews, and supporting event/message tables. PostgreSQL is the configured database provider.

## Main Backend Modules

- `AuthModule`: admin login, JWT strategy, current admin endpoint, role guard.
- `AttributesModule`: public attributes and protected attribute/group option management.
- `CategoriesModule` and `BrandsModule`: public catalog reads and protected admin CRUD/deactivation flows.
- `ProductsModule` and `ProductReferencesModule`: public product discovery/details plus protected product/reference/stock management.
- `PacksModule`: public pack discovery/details, fixed-pack ordering, customizable pack validation, persisted configurations, sharing, and checkout from configurations; protected pack CRUD.
- `QuizModule`: public quiz questions/profile creation and protected quiz management.
- `RecommendationsModule`: rule-based recommendation generation/session reads and protected rule management/preview.
- `OrdersModule`: public COD order creation and safe lookup, plus protected admin order list/detail/status workflow.
- `MediaModule`: protected Cloudinary-backed media upload and entity image relationship endpoints.
- `WishlistModule`: public anonymous-session wishlist endpoints.
- `ReviewsModule`: public verified-purchase review submission/read flows and protected moderation.

## Authentication And Admin Roles

Admin authentication is implemented with `POST /auth/login`, JWT bearer auth, `GET /auth/me`, `JwtAuthGuard`, `RolesGuard`, and the `AdminRole` enum: `OWNER`, `ADMIN`, and `STAFF`. Most admin read endpoints permit `OWNER`, `ADMIN`, and `STAFF`; mutating admin endpoints generally require `OWNER` or `ADMIN`. No refresh-token flow or admin user CRUD endpoint is present.

Customer authentication is not implemented. Customer-facing flows use anonymous/customer-profile identifiers and order/customer data submitted in request bodies.

## Implemented Public Customer APIs

- Health check: `GET /`.
- Public catalog: categories, brands, attributes, products by list/id/slug, packs by list/id/slug.
- Quiz and recommendations: quiz questions, profile creation, recommendation generation, recommendation session reads, and configuring a recommended pack.
- Pack configuration flow: validate/persist configurations, share configurations, read shared configurations, and checkout from persisted configurations.
- Orders and checkout: COD order creation through `POST /orders`, direct cart-line checkout through `POST /orders/checkout`, fixed-pack checkout, pack-configuration checkout, and safe public order summary lookup.
- Wishlist: add/list/remove wishlist items for a session/customer-profile identity.
- Reviews: submit, edit, delete pending reviews; attach/remove review images; list approved product/pack reviews.

## Implemented Admin APIs

- Admin login/current identity.
- Categories, brands, products, product references, stock counts, packs, attributes, quiz questions, recommendation rules, orders, reviews, media assets, and entity image relationships.
- Order status workflow through `PATCH /admin/orders/{id}/status`.
- Recommendation rule preview through `POST /admin/recommendation-rules/preview`.

## Ecommerce Flows Available

- Catalog/products/packs: implemented for public reads and admin management.
- Cart and checkout: checkout from submitted cart lines exists, but there is no persistent cart resource.
- Orders and status workflow: implemented for COD orders and admin status changes.
- Stock/product references: product references and admin stock-count updates are implemented; deployment should verify real stock reservation/deduction expectations before live traffic.
- Quiz and recommendations: implemented as a rule-based V1 flow using customer profiles, attribute answers, recommendation rules, and pack/product/reference scoring.
- Reviews/feedback/media: reviews and image attachments are implemented; feedback beyond reviews is not exposed as an API. Media is Cloudinary-backed behind the media service/provider layer.

## Partial Or Missing Capabilities

- No customer account/authentication flow.
- No refresh-token flow for admin sessions.
- No admin user management API.
- No persistent customer cart resource despite checkout from cart-line payloads.
- Cash on Delivery is the only payment method; no online payment provider.
- No delivery-provider integration or shipment tracking API.
- No WhatsApp/SMS/email provider integration despite message/event tables.
- No direct browser-to-Cloudinary signed upload; uploads pass through the backend.
- No dedicated brand-logo, attribute-option image, or quiz-option image relationship endpoint; URL fields exist for some of these objects.
- Recommendation engine is rule-based V1, not ML/personalization beyond configured rules and attributes.

## Main Deployment Risks

- Live launch depends on correct environment configuration: database, JWT secret, Cloudinary credentials, CORS origins, and seed/admin setup.
- Customer identity is anonymous/profile-based, so fraud prevention, account history, and authenticated self-service are limited.
- Checkout/order flows need operational confirmation around stock reservation/deduction and cancellation/return handling before real customers.
- COD-only payment and no delivery integration mean manual operations remain required after order creation.
- Public order lookup is intentionally limited, but production should still review whether ID-only lookup is acceptable for the business risk profile.
- Media upload limits and Cloudinary failures should be tested in the deployment environment.

## Deployment Verdict

Ready for internal testing.

The backend builds, Prisma validates, OpenAPI generation/checks pass, and the unit test suite passes. It is not ready for real customers until P0 operational gaps around production configuration, stock/order behavior, and customer/order risk controls are explicitly accepted or fixed. MVP launch is plausible with conditions after those checks are complete.
