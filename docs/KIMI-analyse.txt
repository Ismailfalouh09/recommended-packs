1. OVERVIEW
--------------------------------------------------------------------------------
This is a NestJS backend for a beauty product recommendation and Cash-on-Delivery
order system. It exposes:

- Public APIs for quiz/profiles, product/pack catalog, recommendations, and orders
- Protected admin APIs for catalog, packs, quiz/attributes, recommendation rules,
  order workflow, and media/image management
- JWT-based admin authentication with role-based authorization (OWNER, ADMIN, STAFF)
- PostgreSQL persistence via Prisma ORM
- Cloudinary-backed image storage with metadata kept in PostgreSQL

Current documented stopping point: Task 15.5 "Admin Dashboard Backend Readiness"
on branch feature/task-14-media-management.

2. TECH STACK & ARCHITECTURE
--------------------------------------------------------------------------------
Strengths:
- Clean modular NestJS structure (modules, controllers, services, DTOs)
- Prisma as the single database access layer through PrismaService
- class-validator / class-transformer for input validation
- Swagger/OpenAPI auto-generated and committed to docs/openapi.{json,yaml}
- bcrypt for admin password hashing
- passport-jwt for token validation
- Soft-delete / archive patterns instead of hard deletes for most entities
- Transactional writes for nested create/update flows (products, packs, quiz, orders)
- Media abstraction: Cloudinary SDK isolated in the provider layer; feature services
  use MediaService rather than calling Cloudinary directly
- Tests exist at unit/service level and e2e level

Architecture notes:
- Controllers are intentionally thin; business logic lives in services
- Prisma 7 with custom prisma.config.ts for datasource URL handling
- CORS is configurable via ADMIN_DASHBOARD_ORIGIN for the future admin dashboard
- OpenAPI generator uses ts-node because tsx did not emit DI metadata during bootstrap

4. API COVERAGE
--------------------------------------------------------------------------------
Public endpoints (no auth):
- GET /, GET /attributes, GET /attributes/:code/options
- GET /quiz/questions, POST /quiz/profiles
- GET /products, GET /products/:id
- GET /packs, GET /packs/:id
- POST /recommendations, GET /recommendations/:sessionId
- POST /orders, GET /orders/:id

Protected admin endpoints:
- Auth: POST /auth/login, GET /auth/me
- Catalog: categories, brands, products, product references, stock
- Packs: full CRUD with nested items/attributes
- Quiz/attributes/rules: full CRUD plus reorder and preview
- Orders: list, detail, status workflow
- Media: upload, list, metadata update, delete, plus entity image attach/reorder/delete

Role model:
- OWNER/ADMIN: full write access
- STAFF: read-only on catalog/orders/media; can preview recommendations

5. SECURITY REVIEW
--------------------------------------------------------------------------------
Positive:
- passwordHash, JWT_SECRET, DATABASE_URL are excluded from OpenAPI output
- Public order lookup returns a safe summary only (no phone, address, notes, history)
- Admin detail exposes customer PII only to authenticated admins
- JWT payload is minimal (sub, email, role)
- Inactive admins are rejected by JwtStrategy
- ValidationPipe whitelists and forbids non-whitelisted properties
- Image upload validates MIME type, file signature, and max size

Concerns:
- No refresh-token flow; a single access token is used for admin sessions
- No global exception filter adding timestamp/path; error responses use Nest defaults
- Public order creation accepts customer data with no CAPTCHA/rate-limiting documented
- No customer authentication; orders are anonymous by design but this can allow
  brute-force scanning of order IDs if UUIDs were ever guessable
- Brand logos, attribute option images, and quiz option images still rely on plain
  URL fields or future extension points rather than the Cloudinary relationship model
- No documented rate limiting, Helmet headers, or request logging middleware
